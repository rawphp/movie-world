# Ideate — UR-006

**Reviewed:** 2026-07-09

## Explorer — Assumptions & Perspectives

- **"Filtered or not" is ambiguous.** The brief says navigation should work through "the library (filtered or not)". Two readings: (a) navigate the list *as currently displayed* — respecting active filters and sort (`store.list`); (b) always navigate the *full* library ignoring filters. Reading (a) matches user expectation from the LibraryView grid, but if the user meant (b), the decomposition changes. Scenario: user filters to "Action", opens a movie, presses next — do they expect the next Action movie or the next movie alphabetically overall? The brief triggers this because it explicitly parenthesizes "(filtered or not)" without resolving it.
- **"A keyboard combination" is actually two.** Previous and next are distinct actions, so settings must store and edit two combinations (or one modifier scheme + two direction keys). The brief's singular phrasing ("a keyboard combination") hides this; the settings UI and storage schema need to be designed for a pair.
- **No default combination is specified.** The feature ships with *some* default (e.g. `Cmd/Ctrl+←` / `Cmd/Ctrl+→` or bare arrow keys). Bare arrows conflict with page scrolling and text inputs; a modifier default is safer. Whichever is picked becomes a de facto product decision the brief doesn't make.
- **Sort order matters as much as filters.** `store.list` applies `sortMovies` after `filterMovies` (src/renderer/src/stores/library.ts:21-23). "Previous/next" only has meaning relative to the current sort key. The brief never mentions sort, but navigation must follow the displayed order or it will feel random.

## Challenger — Risks & Edge Cases

- **Current movie absent from the filtered list.** The filter state persists in the Pinia store. If the user opens a detail view and the movie later drops out of the filtered list (filter changed, metadata update changes its genre/year, match fixed), "next from current position" has no anchor. Scenario: movie updates via `onMovieUpdated` while detail is open and no longer passes the filter — pressing next must do something sane (no-op, or nearest neighbour) rather than throw. Triggered by "navigate to the previous or next movie in the library (filtered or not)".
- **Shortcut firing while typing.** The detail view can open FixMatchDialog, which contains a search input; Settings has text inputs. A keydown listener that doesn't guard against `event.target` being an input/textarea (or the dialog being open) will hijack keystrokes. Scenario: user types a movie title containing the bound key in the Fix-match search and the app navigates away, losing their dialog state. Triggered by "if I press a keyboard combination".
- **Boundary behaviour undefined.** At the first movie, "previous" has no target; at the last, "next" doesn't. Wrap-around vs. no-op is unspecified and needs a decision plus a test. Single-movie library and empty-list (all filtered out) are the degenerate cases.
- **Editable shortcut needs validation and conflict handling.** A free-form "editable in settings" field can capture unusable combos (e.g. `Cmd+Q`, bare `Escape`), duplicates (prev == next), or empty values. Scenario: user binds both actions to the same key, or binds `Cmd+W` and closes the window instead of navigating. Settings UI needs a capture-style recorder or at minimum validation + reset-to-default.
- **The settings store has no generic setter.** `createSettingsStore` (src/main/settings.ts) exposes only `setApiKey`/`addFolder`/`removeFolder`, and the `Settings` shared type has only `folders` + `tmdbApiKey`. Persisting keybindings requires a shared-type change, a new setter, a new IPC channel (`src/main/ipc.ts`), and a preload bridge method — this feature is *not* renderer-only, unlike the recent UR-004/UR-005 detail-view work. Existing settings files on disk must also merge cleanly (the `{ ...DEFAULTS, ...parsed }` spread handles this if defaults are added).

## Connector — Links & Reuse

- **`store.list` is the canonical ordering.** The filtered+sorted list already exists as a getter (src/renderer/src/stores/library.ts:21). Prev/next can be computed by finding the current id's index in `store.list` — no new filtering logic needed, and it automatically honours reading (a) of the ambiguity above.
- **Navigation is a router push.** Detail routes are `/movie/:id` (src/renderer/src/router.ts); prev/next is just `router.push({ name: 'movie', params: { id } })`. The view already reacts to `route.params.id` via a computed, so the component doesn't need remounting logic — worth verifying the lazy-loaded component re-renders on param change (same-component navigation reuses the instance).
- **Settings plumbing pattern is established.** `settings:get` / `settings:set-api-key` IPC + preload pattern (src/main/ipc.ts:12-13, src/preload/index.ts:4-5) is the template for a `settings:set-keybindings` channel; SettingsView.vue's section layout is the template for the new UI block.
- **Decisions memory note:** UR-004/UR-005 scoped shared/main/preload out; this UR *cannot* — the editable-settings requirement forces all four code layers back in scope. Don't inherit the prior "renderer-only" framing.

## Summary

The core ambiguity is what "previous/next" means when filters are active — recommend navigating `store.list` (the displayed, filtered+sorted order), with a decided fallback when the current movie isn't in that list. The feature spans all four code layers (shared type, main settings store + IPC, preload, renderer UI + keyboard handling), unlike recent renderer-only URs. The settings side needs real design: two bindings not one, a sensible default, validation against duplicates/unusable combos, and suppression of shortcuts while typing or while the Fix-match dialog is open.
